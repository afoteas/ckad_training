# Alertmanager Routing and Notification Best Practices

Alertmanager is the central hub for all alerts generated by Prometheus. It handles grouping, deduplication, silencing, inhibition, and routing to the correct receiver.

## Core Concepts

| Concept | Description |
|---|---|
| **Receiver** | A named destination: Slack channel, email address, PagerDuty API key |
| **Route** | A set of label-matching rules that map incoming alerts to a receiver |
| **Inhibition** | Suppresses lower-priority alerts when a higher-priority root-cause alert is already firing |
| **Silence** | Time-bound administrative mute for alerts matching a specific set of labels, used during planned maintenance |

## Example Routing Config

```yaml
route:
  receiver: team-dev
  routes:
    - match:
        severity: critical
      receiver: team-ops

receivers:
  - name: team-dev
    slack_configs:
      - channel: '#dev-alerts'
  - name: team-ops
    slack_configs:
      - channel: '#ops-alerts'
```

- Default: all alerts go to `team-dev` (`#dev-alerts`)
- Override: alerts with `severity: critical` go to `team-ops` (`#ops-alerts`)

## Best Practices

- always include a `severity` label (`warning`, `critical`, `info`) in PrometheusRules so routes can prioritize
- route by application or namespace label — don't funnel everything to a single list
- use `group_by: [cluster, alertname]` to bundle related alerts into a single notification
- for critical alerts, integrate with on-call tools like PagerDuty or OpsGenie so alerts escalate if unacknowledged
- always set an expiry time on silences; a silence without an expiry can hide real outages indefinitely

## Inhibition Example

If a node is down, suppress all pod-level alerts for pods on that node to avoid hundreds of redundant notifications:

```yaml
inhibit_rules:
  - source_match:
      alertname: NodeDown
    target_match_re:
      alertname: Pod.*
    equal: [node]
```

## Operational Considerations

- receiver misconfiguration (stale Slack channel, wrong API key) silently drops critical alerts — test regularly
- inhibition rules that are too broad can suppress unrelated critical alerts; test thoroughly before applying to production
- run Alertmanager as a clustered set of instances using gossip protocol for high availability and to avoid duplicate notifications
- secure the Alertmanager web UI and API with Ingress authentication or RBAC; the API exposes all active alerts and allows creating silences
